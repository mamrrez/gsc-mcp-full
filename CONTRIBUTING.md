# Contributing

Thanks for helping. The most valuable contributions are **language rules** and
**real-world query samples** — the engine is only as good as the folds it knows.

## Setup

```sh
git clone https://github.com/mamrrez/gsc-mcp-full && cd gsc-mcp-full
uv venv && uv pip install -e ".[dev,all]"
uv run pytest
uv run ruff check --fix
```

Tests need no network and no credentials: the tools run against a fake
Search Console in `tests/test_client_and_tools.py`.

## Adding a language rule

1. Add the fold to `src/gsc_mcp_full/i18n/normalize.py`. Decide whether it is
   **standard** (the same word typed differently — safe to merge always) or
   **loose** (near-spellings, merged only on request). When in doubt, loose.
2. Never change the displayed query. Only the match key changes.
3. Add a test in `tests/test_normalize.py` with real queries: at least one pair
   that *should* merge and one that *should not*.
4. If the rule needs a keyboard layout, digit set or script range, add it to
   `keyboard.py` / `scripts.py` with a comment saying where the table comes from.

## Adding a tool

Tools are thin: fetch rows through `Runtime.fetch` (or the store), call a pure
function in `analysis.py` / `i18n`, format with `format.py`. Put the logic in
the pure function and test it there; add one end-to-end test through the fake
client. Keep output compact — cap rows and say so.

## Pull requests

- One change per PR, with a line in `CHANGELOG.md` under *Unreleased*.
- `ruff` clean, `pytest` green on 3.10.
- Docs live in `docs/`; the tool reference (`docs/tools.md`) is generated by
  `scripts/gen_tools_doc.py` — run it if you changed a tool signature or docstring.
